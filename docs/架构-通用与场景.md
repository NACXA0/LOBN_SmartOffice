# 架构：通用管理 · 场景 · HA

> 回答 README 里的两条：界面怎么分、里门常开时系统能否脱离预约仍运行。  
> 对标：Home Assistant Areas、NetBox Site/Location、安防 Scope（Qumulex）、视觉多站点「同库不同镜头」。

## 结论（先读）

1. **不要**为「通用」和「教室」各抄一套人员/资产/监控模块。  
2. **要**：**一套资源注册表 + 作用域（scope）视图**；场景只是「绑定若干空间 + 可选适配器」的透镜。  
3. **HA** 只管设备实体与保命执行；**SmartOffice** 管判断与台账；**场景仓库**（如 FireClassroom）只管钱/单据/预约，并可关闭而不拖死总管。

## 三层边界

| 层 | 管什么 | 不管什么 | 例子 |
|----|--------|----------|------|
| **HA** | 实体、脉冲、climate/light 执行、保命按钮、仪表盘读数 | 「这是谁」「该不该开」「滞留」 | ESPHome 门板、开关、传感器 |
| **SmartOffice 通用** | 店内事实：人、空间、门策略、资产、监控取帧、告警、造访 | 收款、排课 UI、专有 WiFi 套餐编辑 | 大门、全员档案、Frigate 预览 |
| **场景（透镜）** | 同一套资源的**过滤视图** + 场景专有插件 | 第二份人员底库 | 「教室 A」：本教室在场的人、里门、教室屏 |

```text
                    ┌─ 场景：教室（适配器：预约）
店内资源注册表 ────┼─ 场景：未来其它生意…
（人/空间/资产/门） └─ 通用：无场景过滤 = 全店
         │
         ▼ 意图 MQTT
        HA 实体执行
```

## 重复功能怎么处理？

成熟项目几乎都选 **「同一功能，作用域不同」**，而不是「按作用域各写一套」：

| 项目 | 做法 |
|------|------|
| **Home Assistant** | Device/Entity 一份；Area/Floor 只是分组与自动化目标 |
| **NetBox** | Device 一份；Site → Location 过滤查询 |
| **安防 Scope** | 门/摄像头一份；Places 树决定「看见哪一段」 |
| **多站点视觉** | Camera/规则一份；Org → Site → Area 级联权限 |

### SmartOffice 映射

| 能力 | 数据主人 | 通用视图 | 场景视图（教室） |
|------|----------|----------|------------------|
| 人员 | 全局 `persons` + `visits.space_id` | 全店档案 / 造访 | **过滤**：本场景空间内造访或当前在场 |
| 资产 | 全局 `assets` + `space_id` | 全店台账 | 本场景空间内资产 |
| 监控 | Frigate/go2rtc 流，挂在 `spaces.camera` | 大门与公共区 | 该场景绑定摄像头 |
| 门 | `spaces`（kind=door）+ `access_mode` | 大门策略 | 里门策略（可常开） |
| 设备 | **HA 实体**（ESPHome 等） | 总管只读/发意图 | 场景页深链到 HA 区域或只展示本空间相关实体 |
| 网络/WiFi | **场景专有**（不做进总管底库） | — | 教室网络管理 → 场景仓库或专用页 |
| 预约 | 场景适配器 → `policy_windows` | 可关 | 教室打开时注入策略窗口 |

**原则**：UI 可以「看起来像两套菜单」，API/库表必须是一套；场景页 = `?scope=scene:classroom` 或路由 `#/scenes/classroom/...` 带相同组件。

## 信息架构（工作台）

```text
总览（全店）
通用 ── 空间 · 人员 · 资产 · 记录 ·（监控入口）
场景 ── 教室 A · 教室 B · …（卡片进入）
         └─ 在场人员 | 本室资产 | 里门 | 监控 | 预约/指引（插件）| 网络（插件）
HA   ── 不在 SmartOffice 里复制设备台；需要时 Ingress/深链到 HA
```

- **大门**：通用空间（或「门禁」集合），常走刷脸 / 策略。  
- **里门**：也是 `spaces`，`access_mode=always_open` 时不拦人，但 **presence / 造访 / 陌生人建档照常跑**。

## 门禁模式（兼容「里门常开 + 人员仍运行」）

| `access_mode` | 行为 |
|---------------|------|
| `face` | 刷脸/手动才 grant（大门默认） |
| `schedule` | 主要靠策略窗口；可叠加人脸 |
| `always_open` | **不申请开门**（或物理常开）；总管仍识别、记造访、告警 |
| `armed_only` | 仅布防时段才限制 |

**预约关掉时**：`ScheduleAdapter` 未配置云端则直接不启动；已配置但拉空/失败只影响策略开门。`face` / `always_open` / 监控 / 人员档案 / 陌生人建档 / 资产 RFID **全部继续**。总管不依赖场景仓库进程。

**里门常开怎么配**：为里门建 `spaces`（绑该摄像头），`access_mode=always_open`。人过门仍识别、记造访、陌生人入库告警，但**不发** `business/access/grant`。大门可另设 `face`。

## 设备管理边界

| 类型 | 归属 |
|------|------|
| ESPHome 门控、继电器、门磁 | HA 设备；SmartOffice 只发 `business/access/grant` / 读状态 |
| 教室智能屏、空调、灯 | HA 实体（可划 Area=教室）；场景页展示/意图，不另建设备库 |
| 「教室网络管理」 | **场景专有**，不进 SmartOffice 核心；链到场景后台即可 |

## 落地清单（渐进）

1. 文档与路由：通用底栏不变；增加「场景」入口（先教室）。  
2. `spaces.access_mode` + 场景绑定表 `scenes` / `scene_spaces`（空间可属于多场景标签，但物理 Area 唯一）。  
3. 人员/资产列表支持 `space_id` / `scene_id` 过滤（同一 API）。  
4. 里门 `always_open` 验收：无预约、里门不 grant，造访与陌生人仍入库。  
5. 场景专有插件（预约、WiFi）以适配器注册，可卸载。

## 反模式

- 教室人员表与办公室人员表各一份（同步地狱）。  
- 在 SmartOffice 里复刻 HA 设备管理台。  
- 预约服务挂了导致识别/造访/告警全停。  
- 把「场景 UI」做成分叉代码，而不是 scope 参数。
